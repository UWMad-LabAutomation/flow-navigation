CURRENT SIMULATION AND CAMERA SCANNER

ROS 2 Jazzy, Gazebo Harmonic, Nav2, and RViz run together in WSL2. A generated
maze supplies matching Gazebo walls and an occupancy-grid map. AMCL estimates
the robot's pose, SmacPlannerHybrid plans routes, and MPPI Omni drives
the simulated FLOW base. RViz displays the map, costmaps, scan, and planned path.
The changes and validation below concern simulation. Physical camera integration
was not tested in this checkout.

A CPU ray-based approximation of the RealSense D435i now supplies /scan.
The simulation pipeline is:

  CPU ray casting against Gazebo collision geometry
  -> synthetic /camera/depth/points (PointCloud2)
  -> existing camera_to_scan -> /scan (LaserScan) -> Nav2

No LiDAR sensor or depth-image renderer runs in the default CPU mode. The
existing camera_to_scan node is the sole /scan publisher. The optional
rendered camera remains available with camera_backend:=render; only that
mode needs the earlier Gazebo projection correction. Gazebo and RViz windows
still render when enabled, but CPU sensing also runs without either display.

The camera mount defaults to X=0, Y=0, Z=2.0 m, approximately the highest
position with the elevator fully extended. The supplied D435i specifications
are 87 degrees horizontal by 58 degrees vertical FOV, 0.3-3.0 m depth range,
and a 1280x720 image profile at 30 FPS. Simulation samples the same viewing
volume using an adjustable 80x45 ray grid at a requested 30 Hz of simulation
time. This sparse sampling is separate from the physical camera resolution.
Auto pitch is about 26.48 degrees down at 2.0 m, placing the lower FOV edge
on the ground 1 m beyond the robot's front edge.

The point cloud is transformed and height-filtered to remove floor returns
before projection into /scan. AMCL, the obstacle costmaps, and collision monitor
use this camera-derived scan. The height filter retains points 0.10-1.00 m
above ground. Missing returns remain unknown. The simulation models geometric
coverage and occlusion, including moved and inserted obstacles, but it does
not have exactly the same perceptive abilities as a real D435i: sparse rays,
collision meshes, stereo failures, noise, lighting and material effects can
change detections. Hardware validation is still necessary.

The intended physical-robot pipeline remains:

  D435i -> RealSense ROS driver -> PointCloud2
  -> camera_to_scan -> /scan -> Nav2

The CPU plugin is simulation-only and is not part of that hardware pipeline.
No physical RealSense bringup launch exists in this checkout, so this work
does not establish that hardware launch or driver integration is complete.

VALIDATION OF CPU CAMERA MODE

The plugin and simulation packages build with colcon. Live tests without a
display checked both FOVs, cloud coordinates, a collision-only reference wall,
dynamic obstacle insertion/movement, first-hit occlusion, and near/far depth
clipping. A full 21x21 maze test with seed 2305920845, 80x45 rays and no GUI
produced approximately 11.7 /scan messages per wall-clock second at a requested
30 Hz of simulation time. Nav2 became active in about 8 seconds from launch,
with the test supplying the initial pose automatically. A short NavigateToPose
goal succeeded with error code 0. /scan had exactly one publisher,
camera_to_scan, and measured scan age was about 1-2 ms in simulation time.
These measurements are specific
to this WSL run and do not guarantee GUI performance or full-maze reliability.

The earlier 160x90 ray trial was slower in the large maze (about 4 scans/s),
so the default was reduced to 80x45. The earlier rendered-camera path used
CPU software rendering (llvmpipe) and was much more demanding. Simulation
launches now isolate Gazebo topics and use the current world's clock to avoid
interference from leftover Gazebo servers. CPU world generation also replaces
the ground-plane collision with a thin slab matching the visible floor. This
fixes inaccurate ray intersections from DART's oversized internal plane box,
which otherwise produced false floor obstacles. Floor height and the existing
0.10-1.00 m obstacle filter are preserved. A live floor regression test measured
less than 0.4 mm height error. The source SDF is unchanged; the finite floor
extends over the visible 100x100 m area in the supplied world.

CURRENT FORWARD-PREFERRED HOLONOMIC CONFIGURATION

The latest user requirement is to walk forward like a person on clear paths,
with sideways motion available for obstacle avoidance. MPPI remains Omni, with
1000 trajectories, 48 steps and model_dt=0.05 s (2.4 s horizon). Forward and
lateral limits remain 0.63 m/s; reverse is limited to 0.10 m/s and yaw to
0.8 rad/s. The dedicated limiter still caps hypot(vx,vy) to 0.63 m/s.

Hybrid A* now uses forward Dubins paths. PathAngle/PreferForward and path-
orientation alignment favor facing the route. Twirling weight is reduced from
10 to 0.5 so necessary turns are permitted. The initial native-critic-only
trials still allowed sideways startup, so a workspace ForwardTravelCritic now
scores excessive predicted body-lateral velocity inside MPPI. Clear-path
weight is 60 outside a 15-degree forward cone. It reduces to 4 only when facing
the route within 0.5 rad and a known lethal obstacle lies within 1.5 m ahead.
It uses the existing local costmap and does not clip lateral commands afterward.

D435i IMU AND WHEEL ODOMETRY FUSION (2026-10-28)

The default simulation now enables use_imu:=true. Gazebo's physics IMU shares
the camera's adjustable mount and supplies gyro/accel at requested 100 Hz.
It requires no image renderer. Synthetic absolute attitude is marked unavailable
and is not fused. Explicit simulation covariance accompanies the measurements.
The new robot_state_estimation package uses robot_localization EKF at 50 Hz:

  wheel vx/vy/yaw rate + camera gyro -> filtered /odom
  EKF owns odom -> base_footprint; AMCL continues to own map -> odom.

The filter transforms all gyro axes from the pitched sensor frame into the base
frame before applying planar constraints. It retains wheel lateral velocity for
holonomic navigation. IMU orientation and acceleration are excluded: the D435i
has no absolute yaw reference, and gravity/elevator/arm motion must not become
base translation. Raw Gazebo odometry TF is not bridged when EKF is enabled.
use_imu:=false restores the previous wheel-only simulation pipeline.

A synthetic sensor test deliberately biased wheel yaw rate to 0.30 rad/s while
the pitched-camera gyro represented a true 0.20 rad/s. The EKF estimated
0.20025 rad/s and preserved 0.20 m/s lateral velocity. This verifies that the
IMU affects the estimate and that the camera tilt is handled correctly.

The standard obstacle course passed with the IMU/EKF enabled. Three planning
queries and three actual navigation goals succeeded, including a newly inserted
unmapped obstacle. Actual endpoint errors were 0.297, 0.072 and 0.206 m. Peak
command speed reached the 0.63 m/s limit, lateral command reached 0.369 m/s,
and measured body-lateral travel was 2.794 m. Camera_to_scan remained the sole
/scan publisher. Physical D435i hardware was not connected/tested; full-maze
reliability and moving-elevator calibration remain open.

Physical configuration is documented in src/robot_state_estimation/README.md:
enable_gyro:=true enable_accel:=true unite_imu_method:=2 on the RealSense driver,
then supply its actual combined IMU topic and the base wheel odometry to the
standalone state_estimation.launch.py. Hardware must use measured camera TF
and sensor/wheel covariance. IMU fusion can improve short-term odometry; it does
not supply absolute map position or remove every AMCL map-matching failure.

LATEST IMU ACCURACY AND FORWARD STARTUP CHECKS (2026-10-28)

A 24.035 s empty-world physics test exercised straight forward travel, a left
curve, a curved sidestep, forward travel again, and stopping. Gazebo ground
truth was interpolated to each IMU/EKF simulation timestamp, not compared at
mismatched receive times. Gyro rate RMSE was 0.001019 rad/s; integrated gyro
heading maximum error was 0.043 degrees. EKF position RMSE was 6.78 mm and

not physical RealSense calibration. No absolute simulator attitude entered
navigation. AMCL map pose remains a separate source of uncertainty.

Clear-start validation used an empty room with boundary walls outside the
1.5 m front-avoidance zone at startup. Two turning/forward goals succeeded.
Body-forward displacement accounted for 99.94% and 98.82% of traveled distance.
The first 0.5 m stayed inside the forward 87-degree horizontal window for
100% and 90.85% of measured translation, respectively. Small tracking/turning
corrections are allowed; this is forward preference, not a visibility guarantee.

The inserted-obstacle course also passed all three goals. Peak lateral command
was 0.0849 m/s with 0.452 m of measured body-lateral travel, demonstrating that
avoidance corrections remain available. Peak total command speed was 0.63 m/s.
Timestamp-matched EKF maximum errors during this course were 7.0 mm / 0.244
degrees; AMCL map-pose maximum errors were 0.146 m / 3.25 degrees. Thus accurate
IMU odometry does not make global map localization exact.

The user's actual maze seed, 1400869175, starts facing an east wall with the
open passage to the south. A new short test navigated from (-22.5,22.5,0) to
(-22.5,20.8,-pi/2). It succeeded at actual position (-22.447,20.731), about

the first 0.5 m was 99.21% forward and entirely inside the forward camera
